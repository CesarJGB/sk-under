# Fase 6.3 · Editor web por cuenta

La web vinculó la sesión Android Global ya emitida de la cuenta de laboratorio, recuperó su partida, subió **1002 gemas** desde un navegador con perfil móvil y verificó el SHA-256 en dos descargas posteriores. Soul Knight 8.8.0 leyó 1002 en la nube y aplicó la copia al archivo local. El inicio directo por correo y contraseña sigue sin un contrato comprobado. ## Vinculación privada

Un operador puede vincular una cuenta autorizada con una sesión previamente emitida. El comando valida la sesión con una descarga real antes de emitir un enlace válido durante diez minutos. El propietario abre el enlace y confirma la vinculación. El enlace se consume una vez y su fragmento se retira de la barra de direcciones. Las operaciones posteriores usan una cookie independiente de UnderDive.

- La cookie dura hasta 90 días y usa `HttpOnly`, `SameSite=Strict` y `Secure` en HTTPS. Se restringen las escrituras de API al origen exacto configurado y a JSON. El identificador de sesión del navegador se guarda como hash. El navegador solo recibe metadatos, gemas y hashes.
- Cada cuenta tiene una identidad interna derivada con HMAC a partir de la identidad del agregado. Se verifica en cada lectura, junto con el acceso a la cuenta asignado al navegador. La comprobación del agregado complementa la autorización de la sesión original. Una cuenta ya vinculada solo admite el enlace de reconexión en el navegador titular mientras su cookie siga vigente.
- Se guardan los secretos de ChillyRoom con AES-SIV autenticado y asociado a la cuenta, en SQLite con permisos `0600`. Se puede vincular y cambiar entre cuentas, renombrarlas y desvincularlas. La desvinculación elimina el acceso y la sesión de nube; los respaldos privados se conservan bajo el identificador de esa cuenta. Una nueva sesión válida de esa misma cuenta puede volver a vincularla. La reconexión requiere un nuevo enlace.
- La edición llama al servicio de gemas de 6.2. Preparar comprueba la lectura que vio el usuario. Confirmar comprueba original y candidato respaldados, vuelve a leer la nube, registra el intento antes de subir y vuelve a descargar para comparar tamaño y SHA-256. Se serializan las operaciones de una cuenta dentro del mismo volumen. Una caída después del envío requiere verificar antes de preparar otra edición. La API de ChillyRoom empleada carece de una precondición remota de escritura verificada, por lo que otro cliente aún podría escribir entre la última lectura y la subida.
- Restaurar exige que la nube siga teniendo el candidato exacto, o informa que el original ya está en la nube. La escritura requiere `SK_CLOUD_WRITE_ENABLED=true` y una autorización explícita para la cuenta. El flujo administrativo anterior sigue disponible en `/partida/laboratorio` con sus controles de acceso originales.

## Despliegue

La comprobación inicial de `api-sk.underdive.space` devolvió `200` en salud y `access_mode=token`. El contenedor de Coolify estaba saludable, sin las variables de sesión de nube ni autorización administrativa, y sin volúmenes. Esa configuración explica los avisos de la versión 6.2. El sitio de Pages en `sk.underdive.space` respondía en `/partida`. Los contextos configurados de la CLI de Coolify devolvieron `401`, de modo que no se aplicaron variables ni almacenamiento al servicio de producción desde esta sesión.

1. Despliega la imagen de la revisión publicada, con el puerto interno 8000 y HTTPS. Configura `VITE_API_BASE_URL=https://api-sk.underdive.space` para el build de Pages.
2. Configura `SK_CLOUD_ACCOUNTS_ORIGIN=https://sk.underdive.space` e incluye ese origen exacto en `SK_ALLOWED_ORIGINS`. Sirve editor y API bajo el mismo sitio HTTPS para la cookie. El sitio alternativo `pages.dev` puede requerir un proxy de API en su propio origen o redirigir al dominio principal.
3. Monta persistentemente `/var/lib/sk-under/accounts` en el contenedor. La imagen inicializa el directorio con modo `0700` y propietario `10001:10001`. Si el montaje es un directorio del host, verifica propietario, modo y acceso de escritura desde el contenedor. Conserva un respaldo privado del volumen y de su clave externa `SK_CLOUD_ACCOUNTS_KEY` (32 bytes aleatorios codificados como 64 dígitos hexadecimales). La clave es solo de runtime. El volumen administrativo de 6.2, si se usa, va en `/var/lib/sk-under/backups`. [Almacenamiento en Coolify](https://coolify.io/docs/applications/configuration/persistent-storage) · [Variables de runtime](https://coolify.io/docs/applications/configuration/environment-variables)
4. Comprueba `GET /api/v1/health` y `GET /api/v1/cloud/accounts` desde el origen del editor. Con el almacén listo verás `configured=true` y `password_login_available=false`. Mantén apagada la escritura global hasta que el operador la apruebe expresamente.
5. Para vincular una sesión autorizada, carga `SK_CLOUD_SESSION_TOKEN`, `SK_CLOUD_UNIQUE_ID` y `SK_CLOUD_DISTRO_ID` en un proceso privado de operador, junto con el mismo origen, clave y volumen de cuentas que usa la API. Ejecuta desde `backend/`:

   ```bash
   uv run --locked python -m app.cloud.accounts --label "Mi cuenta" --expires SEGUNDOS_UNIX
   ```

   Sustituye `SEGUNDOS_UNIX` por la caducidad real. Entrega el enlace por un canal privado. La opción `--allow-write` concede permiso solo a esa cuenta y el interruptor global del backend sigue siendo obligatorio. Los valores de sesión solo son necesarios al emitir el enlace, salvo que también se quiera iniciar el laboratorio de 6.2. Evita copiar el enlace o el entorno a registros de despliegue.

## Pruebas

- API y servicio: 336 pruebas aprobadas y 16 omitidas por requerir muestras privadas. Se cubrieron la persistencia tras recrear la app, cookies, origen y reuso de enlaces, dos cuentas aisladas, rechazo de acceso cruzado, desvinculación, expiración, reconexión, fallo de red, copia corrupta, discrepancia de identidad y cambio remoto concurrente, doble confirmación e intento de subida con resultado incierto. Las pruebas de errores inyectan fallos en el proveedor. El rechazo de contraseñas incorrectas por ChillyRoom sigue pendiente del login directo.
- Frontend: TypeScript, Vite y 12 pruebas Playwright en Chromium, incluidos viewport de 320 px, formulario bloqueado, vinculación, confirmación y cambio de cuenta. El recorrido contra ChillyRoom empleó una cuenta real y Chromium con perfil Pixel 7. La escritura real solo se ejecutó en esa cuenta. Tras reiniciar el backend, la misma sesión volvió a descargar 1002 gemas en Chromium con perfil Pixel 7 y WebKit con perfil iPhone 13. Las dos lecturas se probaron con emulación móvil.
- Cliente 8.8.0, Android Global, AVD API 30: panel con **1002** en nube y **1001** local, confirmación de *Retrieve Progress*, `CloudSaveGameData:CoverPlayerPref()` y `AutoDnloadAsync`. El archivo local `game.data` pasó de 1001 a 1002 gemas y conservó 25 496 bytes. La nube quedó en 1002. Se conservó el original previo a la subida de forma privada.
- Docker: se construyó la imagen y dos contenedores sucesivos abrieron el mismo volumen. Se comprobó UID 10001, SQLite con modo 0600 y escritura deshabilitada.
- La restauración desde la web y el cambio entre dos cuentas se validaron con pruebas controladas. El recorrido real usó una sola cuenta y conservó la modificación ya verificada.

**Alcance alcanzado.** El mínimo quedó operativo en el entorno de pruebas mediante vinculación privada, con el formulario de contraseña visible y bloqueado. La descarga, edición, subida y persistencia del objetivo principal se demostraron con una sesión de ChillyRoom existente. El acceso directo con contraseña y el uso autónomo en producción quedan pendientes. La aceptación por el cliente oficial se comprobó. El acceso de dos cuentas reales y la restauración remota desde la web siguen pendientes.
