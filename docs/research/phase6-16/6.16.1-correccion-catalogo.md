# Fase 6.16.1 — Corrección del catálogo de personajes en producción

**Estado:** corregido y validado con la imagen Docker real del backend. El
despliegue desde Coolify y la comprobación física del desbloqueo siguen
pendientes del propietario. La función de personajes continúa como
**Experimental · E2**.

## 1. Problema observado

Desde la aplicación desplegada en producción, al preparar un desbloqueo de
personajes aparecía:

> No está disponible el catálogo local de personajes.

El backend devolvía `character_catalog_missing`. Las pruebas locales no lo
detectaban porque se ejecutaban desde el repositorio completo, donde
`docs/save-research/catalogs/characters-880.json` existía.

La causa era doble:

1. `backend/app/save_report.py` resolvía el catálogo con
   `Path(__file__).resolve().parents[2] / "docs/..."`. Esa ruta queda fuera de
   la imagen porque `backend/Dockerfile` solo copia `app/` y
   `backend/.dockerignore` no incluye `docs/`.
2. El cargador estaba decorado con `lru_cache(maxsize=1)` y devolvía un catálogo
   vacío cuando la lectura fallaba. Un fallo transitorio o un catálogo ausente
   podía quedar memorizado durante toda la vida del proceso.

## 2. Corrección aplicada

### Fuente única dentro del backend

El catálogo se movió de forma definitiva a:

```text
backend/app/catalogs/characters-880.json
```

No queda una copia documental paralela. Las referencias de la investigación
apuntan ahora al archivo empaquetado. El archivo sigue siendo el mismo catálogo
saneado de 8.8.0: 42 personajes, 105 habilidades y 802 skins.

### Resolución independiente del directorio de ejecución

`backend/app/catalogs/__init__.py` calcula la ruta con:

```python
CATALOG_PATH = Path(__file__).resolve().parent / "characters-880.json"
```

No depende del directorio de trabajo, de `docs/` ni de la raíz del repositorio.
Dentro de la imagen la ruta resuelta es
`/app/app/catalogs/characters-880.json`.

### Caché sin resultados vacíos

`load_character_catalog()` memoriza únicamente lecturas válidas. Si el archivo
falta, no se puede leer o contiene JSON o estructura inválidos, devuelve un
catálogo vacío con `available=False` y un código de error, pero no almacena ese
fallo. Un catálogo reparado o montado después se vuelve a leer sin reiniciar el
proceso.

Los códigos de diagnóstico son:

| `error` | Significado |
| --- | --- |
| `catalog_missing` | El archivo no existe en la ruta resuelta. |
| `catalog_unreadable` | El archivo existe pero no se puede leer. |
| `catalog_invalid_json` | El contenido no es JSON válido. |
| `catalog_invalid_structure` | Falta la estructura esperada o hay códigos, índices, skins o habilidades inválidos. |

Cada fallo se registra una vez en el logger `app.catalogs` con la ruta y el
código, sin incluir datos de la partida. El informe saneado expone
`characters.catalog.available`, `error` y el recuento de personajes, de modo que
el frontend puede distinguir un catálogo vacío de una partida sin personajes.

### Empaquetado y verificación en la imagen

`backend/Dockerfile` conserva `COPY app/ ./app/` y añade, antes de cambiar
permisos:

```dockerfile
RUN python -m app.catalogs.verify
```

El verificador comprueba, durante la construcción:

- disponibilidad y lectura del archivo;
- versión `8.8.0`;
- 42 personajes y 42 códigos únicos;
- 105 habilidades y 802 skins;
- códigos obligatorios y orden observado.

Si el catálogo no se copia o se corrompe, la imagen falla en el build en lugar
de arrancar con un backend incompleto. El mismo archivo queda legible para el
usuario `10001` porque `chmod -R a+rX /app/app` ya se aplica a todo `app/`.

No se añadieron variables de entorno, volúmenes, montajes ni pasos manuales de
Coolify. El contexto de build sigue siendo `backend/`.

### Protección en el frontend

`CharacterUnlockSection` considera el catálogo no disponible cuando
`catalog.available === false` o el recuento es cero. En ese estado:

- muestra un aviso explícito;
- deshabilita la selección y la preparación;
- no permite crear un respaldo ni iniciar la subida.

La validación estricta del backend no se relajó. `character_catalog_codes()`
sigue exigiendo una lista no vacía, códigos de texto únicos, como máximo 42 y
pertenecientes al catálogo. Los códigos desconocidos, repetidos, vacíos o de
tipo incorrecto siguen siendo rechazados con
`invalid_character_selection` o `unknown_character`.

## 3. Prueba de regresión de empaquetado

Se añadió `backend/tests/test_character_catalog.py`. Comprueba:

- que el catálogo está dentro del paquete `app`, no en `docs/`;
- los 42 códigos únicos, 105 habilidades, 802 skins y la versión;
- que un catálogo ausente no envenena la caché y se recupera al aparecer;
- que JSON inválido, estructura inválida y códigos duplicados producen errores
  controlados;
- que una validación de build rechaza contenido incompleto;
- que la ausencia de catálogo bloquea la preparación;
- que `backend/.dockerignore` incluye `app/catalogs/characters-880.json`;
- que el Dockerfile copia `app/` y ejecuta `python -m app.catalogs.verify`.

## 5. Límites de esta validación

- No se desplegó ni reinició el recurso de Coolify desde esta sesión. La imagen
  se validó localmente con el mismo contexto de build.
- No se realizó la prueba física del desbloqueo dentro del juego. Por eso la
  función sigue marcada como **Experimental · E2** y no se modifica
  `gameData.heroUnlock` más allá de lo ya documentado en la Fase 6.16.
- El catálogo sigue siendo una referencia de códigos, índices y nombres. Su
  presencia no demuestra posesión ni sustituye la validación de la partida.
- No se cambiaron gemas, fichas de pesca, `material_fish`, semillas, tickets,
  planos, niveles, habilidades, skins ni el sistema de autenticación.
